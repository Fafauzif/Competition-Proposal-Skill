# Competition Brainstorming

Start with the user's actual idea, materials, judging brief and prior choices. Explain the idea in its strongest plausible form before evaluating it. Show what a user, operator or buyer does and what the intended system changes. Distinguish the user's decisions from your own suggested elaborations.

1. **Read before asking.** Identify the outcome, audience, binding constraints, current evidence, resources and nonnegotiable parts already visible. Inspect existing work and references. Ask briefly about missing choices only when the answer would change what gets built or recommended.
2. **Develop the proposed direction.** Follow one concrete use from trigger through action and handoff to outcome. Identify the owner, authority, resource, and failure or recovery that matters. Make the whole intended proposal visible before discussing the first implementation stage.
3. **Stress-test its central link.** Ask which mechanism changes behavior or operations, how the intervention compares with a real baseline, and whether an important dependency undermines the proposal. Distinguish gaps in explanation from deficiencies in the idea; repair the former directly. Missing proof for a proposed design may call for bounded language, evidence or a targeted test when the claim needs it.
4. **Explore alternatives on purpose.** If you find a substantive weakness or the user asks for options, compare the developed idea with genuinely distinct ways to solve the same problem. Keep the audience, outcome and constraints comparable. Compare meaningful changes to channel, authority, incentives, process or technology. Explain tradeoffs using evidence. Where appropriate, include the current way of working. Recommend a direction and explain what would change that recommendation.
5. **Carry the decision forward.** Capture the chosen idea, why it fits, protected elements, and consequential unknowns. If the user's choice materially changes scope or conclusion, ask before proceeding on that choice. Continue through the normal workflow when the task is clear or the user has already authorized execution and delegated routine choices. A finished artifact request should advance to drafting or production.

When a benchmark informs the idea, use Observe, Imitate, Modify: observe the bottleneck in the current case, identify an attributable mechanism from elsewhere, and explain what must change to work here. Borrow the mechanism after checking fit. Borrow numerical results only when evidence supports a context-specific transfer.

Use [the competition examples](references/competition-ideation.md) for an open direction, a fixed idea, or a benchmark transfer. This method adapts the context-first questioning, concrete comparisons and playback in [Superpowers brainstorming](https://github.com/obra/superpowers/tree/22f0b463e7a5e579904dd6211a520321035526f7/skills/brainstorming).
