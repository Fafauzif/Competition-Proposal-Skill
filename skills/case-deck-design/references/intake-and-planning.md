# Intake and planning

## Establish authority and scope

Resolve each supplied file's role from the current conversation. A PPTX can supply design, reusable objects or content; filenames alone are insufficient.

| Role | What it controls | Mistake to avoid |
| --- | --- | --- |
| Latest user instructions | Scope, behavior and approved changes | Reverting to an earlier outline after a correction |
| Master AI context pack in MD | Thesis, evidence definitions, methods, mechanisms, assumptions | Treating old draft slide copy as more authoritative |
| Current working PPTX | Current design and approved content | Letting donor styling replace the target system |
| Supplied slide bank | Native elements and useful compositions | Importing donor statistics, sources, logos or hidden notes as current facts |
| Raw source files | Unresolved facts and calculations | Asking for data already in a supplied workbook |
| Competition brief | Audience, time limit and slide-count rules | Adding a cover or appendix that violates the count |
| Prototype/screenshots | Proposed experience and visible interactions | Presenting synthetic values as real commitments |

Read the pack fully or in complete ordered chunks. Summarize its argument and distinctions privately. Trace source references where supplied. Identify conflicts with finished slides without editing them. If a conflict materially affects the conclusion, show it in the plan and ask which source should govern new content.

Record absolute file paths and hashes in the task workspace. Do not retain the user's bank, interviews or case claims in this reusable skill. Future tasks use files supplied for that task.

## Questions before a new build

After useful inspection, ask only questions whose answers change the result. Recommend sensible defaults. Common unresolved questions:

1. Which deck supplies the current design, and which slides/objects are finished or editable?
2. What are the required slide count, appendix treatment, pitch duration and audience?
3. Are the recommendation and solution set settled, or are identified argument changes open for discussion?
4. Which quantitative inputs or visuals are missing, and can a nonblocking gap remain labelled?

Do not repeat answered questions. Do not ask users to choose routine spacing, weights, crop coordinates or connectors. Resolve those from the reference. If the user asks for questions, ask meaningful remaining ones; do not invent decisions to satisfy a count.

Use a concrete storyline and donor-element plan when the user asks to see the plan before authoring. If the user has asked for a finished deck, resolve routine design details and proceed with the agreed scope. Ask only about major choices that the existing brief does not settle. For a narrow revision, work within the marked scope and ask before extending it.

## A reviewable pre-build plan

Provide the user's narrative spine and a slide map with meaningful draft headlines.

| Field | Show |
| --- | --- |
| Logical ID/role | Main argument, analysis, solution, implementation, finance, risk or appendix |
| Draft headline | Supported takeaway or clear solution description |
| Argument/evidence | What the slide establishes and the supplied support |
| Main visual | Content-appropriate tree, comparison, journey, chart, table or other asset |
| Donor elements | Exact file/slide and shape IDs, with readable cropped thumbnails |
| Adaptation | What is retained, recombined, repositioned, recolored or replaced |
| Missing inputs | Specific data/asset and whether it blocks the build |
| Preservation | Locked slide, authorized edit, duplicate or new slide |

Show a small set of readable donor crops, not dozens of tiny screenshots. A useful plan may combine folded panels from one donor, an actor handoff from another and an impact-chart arrangement from a third. Explain how those parts will follow the target deck's typography and colors. Do not promise native transfer before checking object editability and dependencies.

Select frameworks for the argument. Do not force the case into a fixed catalogue of consulting frameworks. A solution needs explanation and a mechanism, but not automatically two slides or three boxes. Do not add a benchmark page or standalone overview unless the approved structure needs it.

## Private build records

Use compact JSON or Markdown only where useful:

- Design contract: dimensions, role fonts/sizes, palette, anchors, source style and reference slides.
- Evidence ledger: claim, numerator/denominator, unit, timeframe, source locator, evidence type, caveat and consuming slides.
- Donor map: source hash, slide/object IDs, selection scope, target element, operation, palette mapping and verified reuse status.
- Assembly map: logical IDs, source parts, final order, appendix targets and return links.
- QA record: inspected slides, preservation mapping, findings, fixes, actual checks and final file hash.

Keep build commentary and audit logs out of audience-facing text. Notes can hold sources and purposeful visual instructions, not a narration of tools or validation.

## Revisions after approval

Start from the last approved output. Enumerate the allowed change set privately. Preserve everything else, including native charts, source data and notes. Update navigation by logical destination when slides move.

Condensing a bibliography and categorizing an index can change those slides, count, order and link destinations. It does not authorize edits to solutions, finance or quotations. Prove scope through retained-slide XML/notes comparison and rendered comparison. Do not rerun an older full-deck builder whose broader modifications are no longer authorized.
