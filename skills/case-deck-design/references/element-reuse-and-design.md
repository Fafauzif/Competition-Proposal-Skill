# Element reuse and design

## The core operation

Treat the bank as reusable visual parts. Select an element because it communicates a relationship well, then adapt its arrangement and styling to this case. Reuse native objects where possible; do not merely describe the donor and then create a generic grid.

Useful transfer units include folded panels and their shadows, issue-tree branches, handoff lanes, Gantt bars and milestones, risk-response rows, financial chart/metric arrangements, screenshot callouts and comparison-card structures. Remove old case text, values, logos and citations. Retain useful geometry, grouping and z-order. Elements from several donors can form one new slide. Do not insert donor slides as unexplained extras.

## Inspect hundreds of slides

Inventory every slide in presentation order; part filenames need not equal visible numbers. Attach the bank hash to cached observations. Record native IDs, shape types, text, pictures, tables, charts, groups and theme/layout dependencies.

Render the bank. Review labelled contact sheets in manageable batches, then inspect candidate slides individually at full size. A title may not describe the useful visual within it. A beautiful framework may be one flattened picture. Both visual inspection and structural inventory are necessary.

Search flexibly by purpose: diagnosis, hierarchy, decision, comparison, mechanism, actors, evidence, benchmark, timeline, risk, sensitivity, financial trend and closing. Tags are hints. Assess readability, usable proportions and editability. Keep a donor shortlist by target need, with an alternative when an object cannot transfer intact. Prefer one purposeful readable visual over several tiny screenshots. Duplicate a whole slide only when its composition and content capacity fit.

## Derive the current design contract

Use the latest designated working deck and explicit guidelines. Inspect multiple completed slide roles, not the cover alone.

| Property | Inspect |
| --- | --- |
| Canvas | Exact width, height and aspect ratio |
| Typography | Families/weights for headings, body, numbers and sources; inherited values |
| Hierarchy | Actual point sizes by role; deliberate appendix/chart variations |
| Palette | Colors for hierarchy, emphasis, comparison and implication |
| Anchors | Title, logo, section marker, source band, footer and content bounds |
| Structure | Container geometry, line weights, dashes, arrowheads, shadows, dividers |
| Density | Comfortable line lengths, explanation volume and gaps |
| Emphasis | Selective bolding, large statistics, numbered subheads and implication boxes |
| Assets | Crop conventions, logo proportions, screen formats and backgrounds |

Native styles can inherit through runs, paragraphs, shapes, layouts, masters and themes. Missing explicit declarations are not evidence of default fonts. Use renders and host inspection to resolve inheritance. Never silently substitute a font and claim an exact match.

Standardize role styling and visual language, not every body layout. Do not import a donor's fixed aspect ratio or palette. Native units: 914400 EMU/inch, 12700 EMU/point, 9525 EMU/CSS pixel at 96 DPI. Convert deliberately.

## Recompose deliberately

1. Decide what the reader must understand and which relationship should be visible.
2. Reserve the major visual's readable footprint before supporting text.
3. Choose the smallest coherent donor unit providing that structure.
4. Replace donor text/data while retaining useful geometry and connector logic.
5. Apply current palette, type roles and emphasis. Resize containers independently of text.
6. Add short explanations at the relevant feature, with quantitative impact near its mechanism.
7. Compare with completed target slides at the same scale and refine spacing.

Never scale a text-containing group down to fit. Group transforms can shrink displayed type even when XML run sizes appear unchanged. Recreate text at the target role size, shorten copy, enlarge the visual, change the arrangement or redistribute within the authorized count.

Remove unneeded framework branches and rebalance. Extend useful visual grammar when necessary instead of cramming multiple causes into a tiny box. Avoid arrows that imply unsupported one-to-one relationships. Recompose compatible elements when no whole layout fits; record literal reuse versus reconstruction honestly. No fixed reuse quota is required.

## Track exact elements

Give authored placeholders stable names, such as `reuse.solution.description`, `reuse.issue.branch.left` and `reuse.timeline.bar.1`. Map exact donor object IDs and target placeholders. Record object type, dependency state, whether donor text is cleared, and which style properties the target supplies.

For grouped selections preserve source bounds, z-order and internal connector targets. Do not select both a group and a descendant. Reattach or intentionally remove connector references to unselected objects and inspect the visible line. A valid package can still contain a misleading disconnected arrow.

Tables and charts carry content. Their dimensions, labels, values, units and editable data sources must fit the current argument. Copying chart appearance never authorizes copying old numbers. Use the host's native chart workflow when a direct transfer cannot preserve dependencies reliably.

Ask only for real conflicts: competing style authorities, missing required fonts, or a fixed count incompatible with required legible content. Resolve routine choices independently. Preserve locked-slide defects and report material ones separately; new slides should follow the intended design rather than reproduce accidental clipping.
