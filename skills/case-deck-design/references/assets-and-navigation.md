# Assets, sources and navigation

## Purposeful visual assets

Use the supplied prototype and screenshots to understand real demo interactions before selecting visuals. A stateful app may require a proposal, booking or support case before a screen exists. Keep existing prototype and proposed extension distinct. Do not invent routes or deep links. If the user will capture screens, provide verified URLs plus state/setup steps and the exact content required; do not force a phone capture when a desktop view is appropriate.

Reserve realistic readable proportions. Mobile traveler flows can use phone frames; a support-agent workspace usually needs a browser frame. Crop irrelevant browser chrome or empty screen regions while preserving meaningful labels, totals, conditions and actions. Keep original image pixels and use native crops when supported. Never stretch a phone screen into a desktop aspect ratio or reduce several screenshots until their content is unreadable.

Every placeholder or asset instruction must specify:

| Field | Meaning |
| --- | --- |
| Format | Phone, browser, offer card, chat, photo, illustration or other asset |
| Content | Exact elements that must be visible |
| Purpose | What the audience should understand |
| Status | Existing prototype, supplied capture, proposed mockup or generated illustration |

Keep visible labels short. Put the detailed instructions in speaker notes or a requested asset brief. A useful placeholder may say "Proposed mockup: replacement options"; its notes specify money due now, refund timing and the next support action. Use only mechanisms supported by the current pack, or label a reasonable extension and surface it in the plan.

## AI-generated imagery

The user is open to generated images outside the app. Use image-generation tools for suitable imagery, not exact quantitative charts, data tables, issue trees or slide text that must remain editable. Keep labels/callouts editable above an image when feasible. For a prompt supplied to the user, include:

- Asset role and its connection to the approved solution.
- Subject, composition, orientation, aspect ratio and required negative space.
- Current design palette and intended placement.
- Necessary details and excluded irrelevant content.
- What should remain text-free for editable slide labels.
- Status as a proposed illustration or mockup, not a real deployed product.

Avoid inventing major features to justify attractive imagery. Do not let a generated screenshot's accidental text or numbers become evidence. Inspect received images before placement; ask for a replacement only when cropping or layout cannot make the intended information readable.

## Audience-facing sources

Keep footer sources concise and useful: author/organization, date where needed, appendix code and a short evidence description. Make appendix codes/internal references clickable and external sources clickable. Do not expose internal filenames, worksheet lists, processing stages or "implications / workbook / product backlog" commentary as the source line. Full source locators can live in notes and appendices.

Follow the current design rules for source fonts and check actual legibility at display size. Shorten visible source wording, use concise appendix references, or change the authorized layout. Preserve required caveats that affect the conclusion.

## APA 7 bibliography

When a bibliography is required, populate it from sources actually cited. Keep a reference ledger containing author, date, title, source/publisher/site, URL/DOI, source type and verification state. Deduplicate by source identity rather than deleting different pages with similar titles. Do not invent authors, publication dates, URLs, access dates or DOIs.

Use APA 7 formatting appropriate to the source type: author/date, title, source and DOI/URL as applicable, title italics and hanging indents. Distinguish unpublished project research/model files from published references. Treat private interviews according to the case's privacy and citation requirements; do not manufacture public bibliographic entries for inaccessible personal communication.

Preserve complete entries while condensing pages. Use two columns with variable-height reference blocks and a legible unchanged font. Balance contiguous alphabetical groups by actual wrap height, not only equal entry counts. Do not delete references, abbreviate away source titles or replace all URLs with "Source" merely to save space.

Long URL runs can wrap differently between authoring and office renderers. A separate indented URL paragraph can avoid hyperlink wrapping problems. Use an APA hanging first paragraph and aligned continuation paragraph; inspect the exported result. Do not use a fixed box height if a long entry needs more lines. The user's past preference for about 3–5 bibliography pages is a useful density preference, not a hard limit for every future source count.

## Categorized table of appendices

Keep actual exhibits and their codes stable unless the user changes them. Group the index by categories derived from the current evidence: research design, business/market, strategic analysis, flight schedules, fare comparisons, search analytics, app reviews, primary survey, anonymous interviews, synthesis or finance are examples, not required categories.

Use meaningful category headers, readable titles and native hyperlinks. Multiple index slides are appropriate when needed. Do not shrink titles to force one index page. Link both code and title where supported, and verify every exhibit appears exactly once unless deliberate cross-listing is requested. Add or retarget a return link to the index page containing that exhibit when within scope.

Use logical IDs and an assembly manifest instead of assuming an appendix code equals its physical slide number. Removing an interview register or inserting bibliography pages can shift all physical positions while codes remain stable. Do not recreate a removed exhibit just to make numbering consecutive.

## Link integrity and privacy

Check every internal target after assembly/reordering and every bibliography URL against the reference ledger. Shape-level and run-level hyperlinks may render differently; verify the native package and the rendered links where the renderer supports them. A working external URL is not proof that it supports the claim.

If anonymity is required, apply it to slide text, notes, images, source labels, alt text, comments, hidden slides and embedded data within the authorized scope. Use provided code names consistently. Do not bundle the name-to-code register with the final deck when the user requested its removal. Keep no respondent data in this skill. Do not silently add or reverse anonymization in an unrelated later revision.
